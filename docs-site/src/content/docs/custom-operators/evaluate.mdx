## `params`

The evaluated parameters, under their declared names, with every check already applied. A parameter that isn't evaluated up front arrives as a handle instead ([Lazy and per-element parameters](/custom-operators/lazy-parameters/)).

## The context

What `OperatorContext` gives a body: `options` (the instance's options with the call's laid over them, read-only), `signal`, `cache` and `trace`, each covered below. The evaluation's data is on it too, as `options.data` (the same object a parameter declared with `default: EvaluationData` receives); Parameters covers that declaration, for a parameter that defaults to the data but can be pointed elsewhere.

## Cancellation

`context.signal`, and `timeoutParam`, which adds a parameter's value to it as a timeout.

{/* NOTE (from Iteration): `context.signal` aborts when the node's result is no longer wanted — `and` / `or` or `find` / `some` / `every` answered early, the evaluation timed out, or the caller aborted. A body doing slow async work should check it (or pass it to whatever it awaits, as the HTTP and SQL clients do). JavaScript can't interrupt code already running, so a slow synchronous body runs to completion and its result is discarded. Concepts (Evaluation, Iteration) say only that work not yet started never runs and requests in progress are cancelled. */}

## Caching

Declaring `cache: true`, and wrapping the slow part of the body in `context.cache.memo`.

{/* NOTE (from Caching and compiling): caching for a custom operator. Its definition declares `cache: true`, and its body wraps the slow part in `context.cache.memo(key, fn)`, choosing a key that covers everything the result depends on, options included (`context.cache.memo(params, () => compute(params))` for a result that depends on its parameters alone). The engine hands a body the live `memo` only where the node is caching, and a passthrough everywhere else, so a body never asks whether it may cache. A `cache: true` operator that never calls `memo` caches nothing, and `memo` on an operator without `cache: true` stores nothing. The engine namespaces keys by operator name and definition fingerprint, runs a key it can't serialize (a function, a class instance, a `Map`) uncached, never caches a failure, and records hits and misses in the trace. The Caching and compiling page ("How long results are kept") links here. Source: "Caching" in docs-dev/v3-specs/v3-operator-contract.md, src/evaluate/memo.ts. */}

## Failing

Throwing `OperatorFailure` with a code and details, and how a failure reaches a fallback.

{/* NOTE (from Writing an operator): the checks on what `evaluate` returns, which Writing an operator only summarises ("checks the result as well, and turns an `undefined` into `null`"). A `NaN` result fails the node with `non-finite-result`, but only from an operator whose `returns` includes `number`: one returning `any` (like `if` or `get`) passes a `NaN` from the data on unchanged. An infinity is a number, and passes, so an `evaluate` function that can make one from finite numbers, as division by zero does, has to fail itself, as the core arithmetic does. A thrown plain `Error` fails the node with `operator-failure`, with the operator's name in front of its message (`formatNumber – …`). Source: normalizeResult and wrapFailure in src/evaluate/operator.ts; #269 for the infinity ruling. */}

## Trace events

Recording events in the trace from inside a body.

{/* NOTE (from Tracing and debugging): a body records an event with `context.trace.note(event)`, where an event is any object with a string `type` and whatever else it wants to carry (`TraceEvent` in src/runtimeInterface.ts). It lands in the `events` of the node's trace entry. When tracing is off, `note` does nothing, so a body calls it unconditionally and pays nothing. Pick a `type` that won't collide with the core ones (`cache`, `request`, `query`, `render`, `key-overwrite`, `shielded-fallback`; `KnownTraceEvent` in src/trace.ts). Say here, too, that because any operator can add its own types, code that reads a trace (a debug panel, a logger) should pass over an event type it doesn't recognise: Tracing and debugging's Events section only says custom operators can record events, and links here. Keep the advice on values: a trace is something hosts log, so don't put secrets in an event (the core events record header names but never values, and SQL text but never its bound values). */}

## What a body must put up with

A body can be cancelled, run more than once, or skipped, since an expression stands for a value. An operator with side effects is responsible for how it behaves when that happens.

The engine-parity helpers, so a custom operator compares, renders and resolves paths exactly as the core operators do.

Failures in expressions need [fallbacks](/guides/fallbacks/) to prevent `evaluate()` from throwing. But a fallback on one node might still allow an uncaught failure on a sibling branch to propagate to the root, and 💥! A plain-value fallback at the root is the sure-fire way to prevent this, but it's a blunt instrument, and you'll usually want fallbacks nearer each failure as well ([Covering the whole expression](/guides/fallbacks/#covering-the-whole-expression)). So it's worth knowing not just _whether_ a failure can reach the root, but _where_ each one can happen, and which fallback will catch it.

That's where `fallbackCoverage()` comes in — a function that tells you if an expression is covered (no runtime failure can reach the root) or not, with a detailed report about the coverage status throughout the expression tree, including which fallback catches each failure.

## `fallbackCoverage()`

```ts title="coverage.ts"
declare const expression: unknown
// ---cut---
import { fallbackCoverage } from 'fig-tree-evaluator/authoring'

const report = await fallbackCoverage(fig, expression)
```

Pass it your FigTree instance and an expression. It checks the expression as that instance would evaluate it, with its operators, fragments and options. It doesn't evaluate the expression, though, so it needs no data.

In this example, a summary line is built from the data:

<Expression
  coverage
  title="Order summary"
  code={`
    {
      $buildString: [
        '%1 placed %2 orders, averaging %3',
        { $upper: '$data.customer' },
        '$data.count',
        {
          $round: [{ $divide: ['$data.total', '$data.count'] }, 2],
          // Uncomment to cover the average
          // fallback: 'n/a',
        },
      ],
    }
  `}
  data={`
    { customer: 'Ada', total: 129.5, count: 3 }
  `}
  caption="Uncomment the average's fallback, and watch the coverage report change."
/>

Each failure that no fallback catches is in `uncovered`, with the `path` to the node where it happens. Here, the runtime data could hold anything, so `upper` may receive something that isn't a string, `divide` may fail its type check on either number, and `count` could be 0.

The report lists only the ways a node can fail. A node that can't, like the `buildString` here, with its template written in and substitutions that accept any value, isn't mentioned at all.

Uncomment the average's fallback in the editor, and `divide`'s three failures move to `covered`. The fallback is on `round`, not `divide` itself, but a fallback covers every node below it, so `divide`'s `coveredBy` names `round`'s path. Nothing catches `upper`'s failure, though, so it's still uncovered.

So in CI, a test can check that no stored expression has anything uncovered:

```ts title="coverage.test.ts"
declare function test(name: string, fn: () => Promise<void>): void
declare function expect(value: unknown): { toEqual(expected: unknown): void }
declare const storedExpressions: Record<string, unknown>
// ---cut---
import { fallbackCoverage } from 'fig-tree-evaluator/authoring'

for (const [name, expression] of Object.entries(storedExpressions)) {
  test(`${name} has a fallback for every failure`, async () => {
    const { uncovered } = await fallbackCoverage(fig, expression)
    expect(uncovered).toEqual([])
  })
}
```

<Callout kind="caution" title="The instance's options, not the call's">
  `fallbackCoverage()` reads the options the instance was created with, so a [`timeout`](/api/options/#timeout) or [`strictDataPaths`](/api/options/#strictdatapaths) you only pass to `evaluate()` isn't in effect. To check under one, pass an instance that has it, such as `fig.with({ timeout: 5000 })`.
</Callout>

The one option of its own, `strictNumbers`, makes it stricter about numbers. By default, it assumes numbers in your data are finite and that arithmetic doesn't overflow. With `strictNumbers: true`, `{ $plus: ['$data.price', 1] }` may also fail with `non-finite-result`, on an extreme number.

## Reading the report

Each finding is one way one node can fail:

```ts
import type { FigTreeErrorCode } from 'fig-tree-evaluator'
// ---cut---
interface CoverageFinding {
  // The node where the failure starts
  path: (string | number)[]
  // The code its error would carry, such as 'type-check'
  code: FigTreeErrorCode
  message: string
  // 'always' if the node fails whenever it's reached,
  // 'may' if it fails for some inputs
  certainty: 'may' | 'always'
  operator?: string
  parameter?: string
  // For a failure inside a fragment: the fragment, and where in it
  // the failure starts. The path is then the fragment call's
  fragment?: string
  fragmentPath?: (string | number)[]
}

// A finding in covered also has:
interface CoveredFinding extends CoverageFinding {
  // The node whose fallback catches it, and where in a fragment
  // that fallback is, if it's inside one
  coveredBy: (string | number)[]
  coveredByFragmentPath?: (string | number)[]
  // The failure is in a fallback that reads $error, so the node
  // returns null rather than the fallback's value
  givesNull?: true
}
```

- **A failure is reported once, where it starts,** never again on the nodes above it. A fallback on that node, or on any node above it, covers it, and `coveredBy` names the nearest.
- **Most findings are `may`.** The analysis goes by the types each operator declares, and by values where it knows them, such as those written into the expression. It knows nothing about your data, so any operator reading `$data` directly may receive the wrong type.
- **A failure in a variable is reported for each place it reaches:** covered where a read of the variable is under a fallback, and uncovered where one isn't.
- **An expression with a [static error](/guides/validation/#static-errors) reports only its static errors,** all `uncovered` and `always`, since `evaluate()` refuses it before anything runs. The first is the one `evaluate()` would throw.
- **Under a `timeout`,** where something in the expression can wait, such as a request, each top-level value without a plain-value fallback gets an uncovered `timeout` finding ([Timeout shielding](/guides/fallbacks/#timeout-shielding)). Once every one has one, each value that can wait gets a covered `timeout` finding instead.

## Custom operators

{/* STAND-IN: Carl to rewrite */}

FigTree knows how its own operators can fail, but not yours. Unless you tell it, it treats a custom operator like a request: something that may fail whatever its inputs, so every node of it gets an `operator-failure` finding, and only a fallback covers it.

The definition's `analysis` field tells it more. Declaring one says how the operator can fail, beyond the [checks FigTree already makes](/custom-operators/writing/#what-the-engine-does-for-you) on its parameters, and that its result depends on its parameters alone, so the analysis can run `evaluate` where it knows them. This operator fails on a string that isn't a date:

<OperatorSource name="daysBetween" />

With both dates written into the expression, the analysis runs it, and knows whether it fails. With either one from the data, it may:

<Expression
  coverage
  throws
  customOperators
  title="Dates known and unknown"
  code={`
    {
      trialLength: { $daysBetween: ['2026-01-01', '2026-03-01'] },
      overdueBy: { $daysBetween: ['$data.dueDate', '$data.today'] },
      // Make this a date, and its finding goes
      daysToGo: { $daysBetween: ['2026-01-01', 'next Tuesday'] },
    }
  `}
  data={`
    { dueDate: '2026-03-01', today: '2026-03-15' }
  `}
/>

<Callout kind="caution" title="Only for an operator whose result depends on its parameters">
  The analysis may call `evaluate` with values from the expression, so an operator whose result depends on anything else, such as one that sends a request or reads the current time, should leave `analysis` out.
</Callout>

Here's the field's shape:

```ts
import type { DeclaredOutput, ExpectedType, FallbackErrorCode } from 'fig-tree-evaluator'
// ---cut---
interface OperatorAnalysis {
  // The ways evaluate can fail. Leave it out if it never fails
  failures?: FailureRule[]
  // The same as leaving analysis out: it may fail whatever its inputs
  external?: true
  // What a node returns, where its inputs narrow its returns
  output?: DeclaredOutput
}

interface FailureRule {
  // The code its error carries
  code: FallbackErrorCode
  // The parameter it's about, which its finding names
  parameter?: string
  // Tests on what parameters receive, by name. The rule holds when
  // every test passes, and always holds without any
  when?: Record<string, FailureTest>
  // Options the failure needs, such as { strictDataPaths: true }
  options?: Record<string, unknown>
  // The tests passing makes the failure possible, not certain
  may?: true
  // Only extreme numbers cause it, so it counts under strictNumbers only
  overflow?: true
}

type FailureTest =
  | string // equals this value
  | number
  | boolean
  | null
  | { type: ExpectedType } // has this type
  | { below: number } // a number less than this
  | { empty: true } // an empty array, string or object
  | { supplied: boolean } // has a value, given or default
  | { invalid: true } // the operator's validate hook refuses it
  | { some: FailureTest } // any element or value passes
  | { not: FailureTest }
```

For example, the core `divide` declares `{ code: 'non-finite-result', parameter: 'by', when: { by: 0 } }`. A test reads what the parameter receives after its default is applied, and `{ invalid: true }` reuses the operator's [`validate` hook](/custom-operators/validate/#the-validate-hook), on a value the hook couldn't see because it was computed.

`output` tells the analysis more about what a node returns than `returns` does. For an operator that returns a count of at least 1, `output: { type: 'integer', min: 1 }` means dividing by its result can't divide by 0. Its other forms are in the `DeclaredOutput` type.

[`defineOperator()`](/custom-operators/writing/#defineoperator) checks `analysis` like the rest of the definition, such as that every parameter a rule names is declared.

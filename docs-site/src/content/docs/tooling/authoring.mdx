Failures in expressions need [fallbacks](/guides/fallbacks/) to prevent `evaluate()` from throwing. But a fallback on one node might still allow an uncaught failure on a sibling branch to propagate to the root, and 💥! A plain-value fallback at the root is the sure-fire way to prevent this, but it's a blunt instrument, and you'll usually want fallbacks nearer each failure as well ([Covering the whole expression](/guides/fallbacks/#covering-the-whole-expression)). So it's worth knowing not just _whether_ a failure can reach the root, but _where_ each one can happen, and which fallback will catch it.

That's where `fallbackCoverage()` comes in — a function that tells you if an expression is fully covered (no runtime failure can reach the root) or not, with a detailed report about the coverage status throughout the expression tree, including which fallback catches each failure.

## `fallbackCoverage()`

```ts title="coverage.ts"
declare const expression: unknown
// ---cut---
import { fallbackCoverage } from 'fig-tree-evaluator/authoring'

const report = await fallbackCoverage(fig, expression)
```

Pass it your FigTree instance and an expression. It checks the expression as that instance would evaluate it, with its operators, fragments and options. It doesn't evaluate the expression, though, so it needs no data.

In this example, a summary line is built from the data:

<Expression
  coverage
  title="Order summary"
  code={`
    {
      $buildString: [
        '%1 placed %2 orders, averaging %3',
        { $upper: '$data.customer' },
        '$data.count',
        {
          $round: [{ $divide: ['$data.total', '$data.count'] }, 2],
          // Uncomment to cover the average
          // fallback: 'n/a',
        },
      ],
    }
  `}
  data={`
    { customer: 'Ada', total: 129.5, count: 3 }
  `}
  caption="Uncomment the average's fallback, and watch the coverage report change. Notice the expression still gives a valid result with this data — the report tells you what *could* fail, not what will."
/>

Each failure that no fallback catches is in `uncovered`, with the `path` to the node where it happens. Here, the runtime data could hold anything, so `upper` may receive something that isn't a string, `divide` may fail its type check on either number, and `count` could be 0.

The report lists only the ways a node can fail. A node that can't, like the `buildString` here, with a plain-string template and substitutions that accept any value, isn't mentioned at all.

Uncomment the average's fallback in the editor, and `divide`'s three failures move to `covered`. The fallback is on `round`, not `divide` itself, but a fallback covers every node below it, so `divide`'s `coveredBy` names `round`'s path. Nothing catches `upper`'s failure, though, so it's still uncovered.

## Reading the report

Each finding is one way one node can fail:

```ts
import type { FigTreeErrorCode } from 'fig-tree-evaluator'
// ---cut---
interface CoverageFinding {
  // The node where the failure originates
  path: (string | number)[]
  // The code its error would carry, such as 'type-check'
  code: FigTreeErrorCode
  // Human-readable explanation of the failure
  message: string
  // Usually 'may' (see below)
  certainty: 'may' | 'always'
  operator?: string
  parameter?: string
  // For a failure inside a fragment: the fragment, and where in it
  // the failure starts. The path is then the fragment call's
  fragment?: string
  fragmentPath?: (string | number)[]
}

// A finding in covered also has:
interface CoveredFinding extends CoverageFinding {
  // The node whose fallback catches it, and where in a fragment
  // that fallback is, if it's inside one
  coveredBy: (string | number)[]
  coveredByFragmentPath?: (string | number)[]
  // The failure is in a fallback that reads $error, so if it
  // happens, the node returns null rather than the fallback's value
  givesNull?: true
}
```

- **Most findings are `may`.** The analysis knows nothing about your data, so an operator reading `$data` may receive the wrong type, or a 0 to divide by: whether it fails depends on what it gets. A finding is `always` only when the node fails every time it's reached, such as `{ $divide: [10, 0] }`.
- **It only reports what can actually fail.** A guarded divide like `{ $divide: ['$data.total', { $plus: [{ $abs: '$data.n' }, 1] }] }` has no divide-by-zero finding, since what it divides by is always at least 1, and a branch an `if` can never take reports nothing.
- **It assumes numbers are ordinary:** finite in your data, and never large enough to overflow. To drop that assumption, pass `{ strictNumbers: true }` as the last argument, as in `fallbackCoverage(fig, expression, undefined, { strictNumbers: true })`, where `undefined` stands in for your own operators' analyses ([Custom operators](#custom-operators)). Then `{ $plus: ['$data.price', 1] }` may also fail with `non-finite-result`.
- **If the expression has a [static error](/guides/validation/#static-errors),** the report shows _only_ those, since the expression is rejected before it even runs.
- **If the instance has a global `timeout`** and the expression has something that can wait, only a plain-value fallback at the top of the expression can fully cover it ([Timeout shielding](/guides/fallbacks/#timeout-shielding)).

## Custom operators

FigTree knows how its own operators can fail, but not yours. Unless you tell it, it assumes a custom operator _could_ fail on _any_ input, so every node that uses it is reported with an `operator-failure` finding, which only a fallback can cover. To get findings as precise as the core operators', declare an **analysis** for each of your operators with `declareAnalysis()`, and pass the list to `fallbackCoverage()` as its third argument:

```ts title="coverage.ts"
import type { ValidatedOperatorDefinition } from 'fig-tree-evaluator'
declare const expression: unknown
declare const median: ValidatedOperatorDefinition
declare const daysInMonth: ValidatedOperatorDefinition
// ---cut---
import { declareAnalysis, fallbackCoverage } from 'fig-tree-evaluator/authoring'

const medianAnalysis = declareAnalysis(median, {
  // How it can fail, and what it returns (see below)
})
const daysInMonthAnalysis = declareAnalysis(daysInMonth, {
  // ...
})

const report = await fallbackCoverage(fig, expression, [medianAnalysis, daysInMonthAnalysis])
```

<Callout kind="tip" title="An analysis is optional">
  An analysis only narrows down what `fallbackCoverage()` would report anyway, so leaving one out breaks nothing. Without it, `fallbackCoverage()` is just a little more cautious, reporting that your operator might fail where it actually can't, so an expression author may add a fallback that isn't strictly needed. That's harmless, and much better than the alternative: _no_ fallback on a node that _could_ fail. So don't let this section put you off writing your own operator. Its analysis can come later, or not at all.
</Callout>

### Where findings come from

The analysis never sees your data. It works from the expression and the operators' definitions, and for each node it works out what each parameter could receive: a fixed value where the expression gives one, like `4` or `{ $plus: [1, 2] }`, and otherwise whatever it could be — anything at all for `$data.input`, or a number for a `multiply` node. That set of values is the parameter's **gamut**.

In the Order summary, `$data.customer` could be anything, so the engine's [checks](/custom-operators/writing/#what-the-engine-does-for-you) narrow it to the type `upper`'s parameter expects, a string: if it isn't one, that's a `type-check` failure, which is the finding you see. Every operator's parameters get these checks, yours included.

The rest are failures only each operator's `evaluate` knows about, like `divide` trying to divide by 0. FigTree can't see inside `evaluate`, so each operator's analysis lists them, as a function of its parameters' gamuts. The core operators' analyses are written just as you'll write yours. Here's `divide`'s:

```ts
import type { OperatorAnalysis } from 'fig-tree-evaluator'
// ---cut---
// The core divide's failures hook, cut down to its one failure
const failures: OperatorAnalysis['failures'] = ({ by }, helpers) => [
  { code: 'non-finite-result', parameter: 'by', occurs: helpers.is(by, 0) },
]
```

`helpers.is(by, 0)` asks whether `by` is 0, and the answer decides the finding:

- **`'yes'`**: `by` is always 0, so the node always fails, as `{ $divide: [10, 0] }` does. The finding is `always`.
- **`'maybe'`**: `by` could be 0, as `'$data.count'` could in the Order summary. The finding is `may`.
- **`'no'`**: `by` can't be 0, as when it's `4`, or `{ $plus: [{ $length: '$data.items' }, 1] }`, which is always at least 1. There's no finding.

### Declaring how it fails

Your own operator's analysis is structured the same way. This `median` operator fails on an empty list, and its analysis says so:

<OperatorSource name="median" />

Register the operator on your instance, and pass its analysis:

```ts title="coverage.ts"
// @filename: operators/median.ts
import type { OperatorAnalysis, ValidatedOperatorDefinition } from 'fig-tree-evaluator'
export declare const median: ValidatedOperatorDefinition
export declare const medianAnalysis: OperatorAnalysis
// @filename: coverage.ts
declare const expression: unknown
// ---cut---
import { FigTree, coreOperators } from 'fig-tree-evaluator'
import { fallbackCoverage } from 'fig-tree-evaluator/authoring'
import { median, medianAnalysis } from './operators/median'

const fig = new FigTree({ operators: [coreOperators, median] })

const report = await fallbackCoverage(fig, expression, [medianAnalysis])
```

With that, the analysis treats `median` like any core operator:

<Expression
  coverage
  throws
  customOperators
  title="Medians"
  code={`
    {
      sample: { $median: [7, 2, 9] },
      scores: { $median: '$data.scores' },
      nothing: { $median: [] },
    }
  `}
  data={`
    { scores: [3, 5, 8, 13] }
  `}
/>

- **`sample`** has no finding, since three values can't be an empty list.
- **`scores`** has two: the type check its parameter gets anyway, and the declared one, since `$data.scores` could be empty.
- **`nothing`** always fails.

When you write the `failures` hook:

- **Declare only what `evaluate` itself fails on:** an `OperatorFailure` it throws, a result that isn't a finite number, or an empty list it can't aggregate. The type checks on its parameters are already read from the definition, so an entry for one would report the same failure twice.
- **`failures: []`** says `evaluate` never fails of itself. Leaving `failures` out says the opposite: the operator may fail on anything, as if it had no analysis.
- **`message`** is a short reason, which ends the finding's message: `median – operator-failure when 'values' is empty`.

### Declaring what it returns

Whether a node can fail often depends on what _another_ node returns, such as a `divide` node whose `by` is your operator's result. Undeclared, your operator could return anything its `returns` allows, so to the analysis, an operator returning an `integer` could return 0. A `gamut` hook narrows that down.

This `daysInMonth` operator always returns 28 to 31, and its `gamut` says so. It also fails on a month outside 1 to 12, which its parameter's type doesn't rule out:

<OperatorSource name="daysInMonth" />

Here, it divides a month's total into a daily average:

<Expression
  coverage
  customOperators
  title="Daily average"
  code={`
    {
      $divide: [
        '$data.monthTotal',
        { $daysInMonth: ['$data.year', '$data.month'] },
      ],
    }
  `}
  data={`
    { monthTotal: 840, year: 2026, month: 2 }
  `}
/>

As we've seen earlier, `divide` normally has a divide-by-zero finding. Here, however, it doesn't, since its `by` can only be between 28 and 31, due to `daysInMonth`'s `gamut` declaration. `daysInMonth`'s own finding, on `month`, is `may`, since `$data.month` could be anything, but it requires an integer from 1 to 12.

Leave the hook out where `returns` already says all there is to say, such as for an operator that can return any string.

<Callout kind="caution" title="A gamut must hold every value the operator can return">
  A gamut that holds values the operator never returns costs only precision, with findings for failures that can't happen. But one that leaves out a value it _can_ return hides real failures, such as a division by zero further up the expression, and FigTree doesn't check it.
</Callout>

### The helpers

`helpers`, the second argument of both hooks, holds the functions for working with gamuts: asking about them, reading from them, and building them.

| `isBelow(gamut, n)`                                 | Is it a number less than `n`?                                                                                      | <SourceLink file="src/authoring/core.ts" find="h.isBelow(exponent, 100)">`power`</SourceLink>                               |

### The declaration in full

```ts
import type {
  Answer,
  FallbackErrorCode,
  Gamut,
  GamutHelpers,
  OperatorAnalysis,
  ValidatedOperatorDefinition,
} from 'fig-tree-evaluator'
declare namespace Authoring {
// ---cut---
function declareAnalysis(
  operator: ValidatedOperatorDefinition,
  hooks: {
    // What a node returns. Leave it out where returns says it all
    gamut?: (params: Record<string, Gamut>, helpers: GamutHelpers) => Gamut
    // How evaluate fails. Leave it out, and it may fail on anything
    failures?:
      | FailureEntry[]
      | ((params: Record<string, Gamut>, helpers: GamutHelpers) => FailureEntry[])
  }
): OperatorAnalysis

interface FailureEntry {
  // The code its error carries
  code: FallbackErrorCode
  // The parameter it's about, which its finding names
  parameter?: string
  // Whether it happens. Left out, it's 'maybe'
  occurs?: Answer
  // It's possible, not certain: caps occurs at 'maybe'
  may?: true
  // Only extreme numbers cause it, so it counts under strictNumbers only
  overflow?: true
  // Options it needs, such as { strictDataPaths: true }
  options?: Record<string, unknown>
  // A short reason, for the finding's message
  message?: string
}
// ---cut-after---
}
```

<Callout kind="caution" title="Declare it for the operator you register">
  An analysis is matched to its operator by identity, so declare it for the same definition object you register. One built separately, such as from a second call to a factory like `sqlOperator(connection)`, is a different operator, and its analysis is ignored.
</Callout>

<Callout kind="tip" title="Analyses in a library">
  In a library, export your operators from your package's root, and their analyses from an `/authoring` subpath of its own, as FigTree does, so an app that never checks coverage never loads them.
</Callout>

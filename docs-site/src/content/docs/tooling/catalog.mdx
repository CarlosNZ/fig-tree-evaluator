So, you're writing a [visual editor](/editor/) for FigTree expressions: it's going to need a bunch of stuff from FigTree — the actual instance, for running evaluations, of course, but you'll also want detailed info about each operator and fragment available, including their parameter declarations so you can enforce correct input in the UI. It'd also be handy to have guidelines about how to _display_ them, such as labels, descriptions and even colours.

Enter the **catalog**: a single source of truth for _all_ that stuff, derived from the FigTree instance itself, along with [listings](/custom-operators/presenting/) you've provided, and structured so it's easy to consume.

## `getCatalog()`

`getCatalog()` takes your FigTree instance, and returns the catalog:

```ts title="catalog.ts"
import { getCatalog } from 'fig-tree-evaluator/catalog'

const catalog = getCatalog(fig)
```

It can also take listings and category changes, to merge over the package's own ([Combining listings](#combining-listings) and [Overriding categories](#overriding-categories)). Here's the shape of what it returns:

```ts title="Types"
import type {
  CatalogCategory,
  CatalogFragment,
  CatalogIssue,
  CatalogOperator,
} from 'fig-tree-evaluator'
// ---cut---
interface Catalog {
  // The categories that have at least one active operator, sorted
  // by each one's order field: logic first, other last
  categories: CatalogCategory[]
  // Both in the order they were registered, with literal last
  // among the operators
  operators: CatalogOperator[]
  fragments: CatalogFragment[]
  // Anything getCatalog() skipped, empty when nothing was wrong
  issues: CatalogIssue[]
}
```

### Operators

Each operator's entry is just what [`getOperators()`](/tooling/overview/#instance-introspection) reports about it, with its listing joined in:

- **`displayName`**: the listing's, or the operator's name where it has none.
- **`description`** and **`docUrl`**: the listing's, absent where it has none.
- **`colors`**: the listing's, or its category's where it has none.
- **`metadata`**: the definition's `metadata`, with the listing's merged over it, so on a clash the listing's wins. It's `{}` when there is none.

And each parameter adds:

- **`description`**: its entry in the listing's `parameterDescriptions`.
- **`seed`**: what an editor should fill in when someone adds the parameter: either the listing's seed, or a generic one for its type ([Type seeds](#type-seeds)) — every parameter has one.
- **`sample`**: a realistic value the parameter could have, from the listing ([Writing a listing](/custom-operators/presenting/#writing-a-listing)), absent where it has none.

The list ends with [`literal`](/reference/operators/#op-literal), which `getOperators()` doesn't report, since FigTree's compiler handles it itself, but which an external tool should treat like any other.

[Joining listings to an instance](/custom-operators/presenting/#joining-listings-to-an-instance) shows a whole entry, for a custom operator.

### What a null does at each parameter

Every parameter carries its [null behaviour](/concepts/evaluation/#null-handling), which FigTree works out when the operator is defined: `nullBehavior` for a `null` in place of the parameter, and, wherever its type allows an array or object, `elementNullBehavior` for a `null` inside it. A fragment's parameters have them too. An editor should show these rather than `nullPolicy`, which is only what the definition declares, and only where the type includes `null`. The operator reference's [Null behaviour column](/reference/operators/#what-a-null-does) is built from them, in the same words:

| `nullBehavior` | A `null` here…                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| `'propagate'`  | makes the whole node return `null`, and the operator doesn't run                                     |
| `'accept'`     | reaches the operator, which decides what it means                                                    |
| `'omit'`       | counts as leaving the parameter out, so its default applies, if it has one                           |
| `'error'`      | is a type error                                                                                      |

## Fragments

A fragment's entry is built the same way as an operator's, from what `getFragments()` reports about it and its listing, with a few small differences:

- Its listing starts from the one on its definition ([Fragments in an editor](/guides/fragments/#fragments-in-an-editor)), and any maps in `listings` are merged over it, so a host can relabel a fragment it didn't write.
- Its `colors` are the listing's, or the package's default pair, [`fragmentColors`](/api/exports/#fig-tree-evaluatorcatalog), where it has none.
- Its parameters have a `description`, `seed` and `sample`, and a null behaviour like an operator's, but no `nullPolicy`: a fragment parameter's type, and whether it's required, decide what a `null` does.

In this example, a map gives `priceWithTax` a display name and a seed, over a listing with only a description:

```ts title="fragments.ts"
import { FigTree } from 'fig-tree-evaluator'
import { getCatalog } from 'fig-tree-evaluator/catalog'

const fig = new FigTree({
  fragments: {
    priceWithTax: {
      expression: {
        $round: [
          { $multiply: ['$params.amount', { $plus: [1, { $divide: ['$params.rate', 100] }] }] },
          2,
        ],
      },
      parameters: {
        amount: { type: 'number' },
        rate: { type: 'number', default: 15 },
      },
      listing: { description: 'A price with a percentage sales tax added, rounded to the cent' },
    },
  },
})

const catalog = getCatalog(fig, {
  listings: { priceWithTax: { displayName: 'Price with GST', seeds: { amount: 100 } } },
})
const priceWithTax = catalog.fragments.find((fragment) => fragment.name === 'priceWithTax')

priceWithTax?.displayName // => 'Price with GST'
priceWithTax?.description // => 'A price with a percentage sales tax added, rounded to the cent'
priceWithTax?.colors // => { background: '#38607e', text: '#ebdf5a' } (default fragmentColors)
priceWithTax?.parameters.amount.seed // => 100
priceWithTax?.parameters.rate.seed // => 1, the generic seed for a number
```

## Combining listings

The `listings` option of `getCatalog()` takes one listing map, or an array of them, each merged over the ones before. That lets you layer listings from different places. For example, a library of custom operators can export listings for them, and you add your own changes on top.[^merging]

In this example, a library exports a listing map beside its operators:

```ts title="geo-operators.ts"
import type { ListingMap } from 'fig-tree-evaluator'

export const geoListings: ListingMap = {
  distance: {
    displayName: 'Distance',
    description: 'The distance between two points on the globe',
  },
}
```

The host passes it to `getCatalog()`, followed by its own changes:

```ts title="catalog.ts"
// @filename: geo-operators.ts
import type { ListingMap, ValidatedOperatorDefinition } from 'fig-tree-evaluator'
export declare const geoOperators: ValidatedOperatorDefinition[]
export declare const geoListings: ListingMap
// @filename: catalog.ts
// ---cut---
import { FigTree, coreOperators } from 'fig-tree-evaluator'
import { getCatalog } from 'fig-tree-evaluator/catalog'
import { geoOperators, geoListings } from './geo-operators'

const fig = new FigTree({ operators: [coreOperators, geoOperators] })

const catalog = getCatalog(fig, {
  listings: [
    geoListings,
    // Merged over the library's listings and the package's own
    {
      plus: { displayName: 'Add' },
      distance: { description: 'Straight-line distance between two places' },
    },
  ],
})

const plus = catalog.operators.find((operator) => operator.name === 'plus')
const distance = catalog.operators.find((operator) => operator.name === 'distance')

plus?.displayName // => 'Add'
distance?.displayName // => 'Distance', from the library
distance?.description // => 'Straight-line distance between two places'
```

Here's how each field is merged:

| Field                                       | A later map's value…                                                    |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| `displayName`, `description`, `docUrl`      | replaces the earlier one                                                |
| `colors`                                    | replaces the earlier pair whole, so a map gives both colours or neither |
| `seeds`, `samples`, `parameterDescriptions` | is merged in per parameter, so a map can change one and keep the rest   |
| `metadata`                                  | is merged in per key                                                    |

So a map holds only what it changes. A field set to `undefined` changes nothing, rather than removing what's beneath it.

  If you publish operators for other apps to use, export a listing map beside them.

[^merging]: That's better than spreading the maps together yourself, since a listing isn't merged as one flat object. A spread would let a later map's `seeds` replace an earlier one's whole, for example, where `getCatalog()` merges them parameter by parameter.

## Overriding categories

Categories have listings too, from the package's `categoryListings`, though you won't need to reach for them too often. The `categories` option changes them. It takes a map or an array of them, merged in order just like `listings`, with each field replaced:

```ts title="categories.ts"
import { getCatalog } from 'fig-tree-evaluator/catalog'
// ---cut---
const catalog = getCatalog(fig, {
  categories: {
    array: { displayName: 'Lists' },
    // The package's orders start at 0, so this puts it first
    data: { order: -1 },
    // A category can also take colors: { background, text }
  },
})

catalog.categories.map((category) => category.displayName)
// => ['Data & objects', 'Logic & control', 'Comparison', 'Arithmetic & math',
//     'Strings', 'Lists', 'Other']
```

<Callout kind="note" title="Category colours are just fallbacks">
  An operator takes its category's `colors` only where its own listing has none, so they can provide an overall fallback for custom operators that lack colour listings.
</Callout>

## Type seeds

A parameter whose listing has no seed starts from `typeSeeds`, by its type:

- **A list of allowed values**, such as `convert`'s `to`, starts at the first one, `'number'`.
- **A union of types**, such as `['string', 'null']`, starts from the first type that isn't `null`.
- **Any other type** starts from its own entry:

| Type                | Seed           |                                                         |
| ------------------- | -------------- | ------------------------------------------------------- |
| `string`, `any`     | `'Replace me'` | visible text, where `null` would show as nothing        |
| `number`, `integer` | `1`            |                                                         |
| `boolean`           | `true`         | since a flag is off by default, and added to turn it on |
| `array`             | `[]`           |                                                         |
| `object`            | `{}`           |                                                         |
| `null`              | `null`         |                                                         |

To start a parameter with something more fitting, give it a seed in [its listing](/custom-operators/presenting/#writing-a-listing).

## Malformed input

`getCatalog()` never throws over what it's given. Listings often come from places the host doesn't control, such as a library or a database of fragments, and one bad value shouldn't break a whole editor. So anything of the wrong type is skipped, and reported in `issues`.

In this example, listings stored as JSON have two mistakes:

```json5
{
  // A displayName must be a string
  plus: { displayName: 42, description: 'Adds numbers together' },
  // A listing must be an object, not just a display name
  subtract: 'Take away',
}
```

```ts title="issues.ts"
import type { ListingMap } from 'fig-tree-evaluator'
import { getCatalog } from 'fig-tree-evaluator/catalog'
declare const storedListings: ListingMap
// ---cut---
const catalog = getCatalog(fig, { listings: storedListings })

catalog.operators.find((operator) => operator.name === 'plus')?.description
// => 'Adds numbers together', since the rest of the listing is kept
```

Here's `catalog.issues`:

```json5
[
  { path: ['listings', 'plus', 'displayName'], message: 'expected string, got number' },
  { path: ['listings', 'subtract'], message: 'expected object, got string' },
]
```

- **A map or a listing that isn't an object** is skipped whole.
- **A field of the wrong type** is skipped alone, and the rest of its listing is kept. `colors` needs both its colours as strings, or the pair is skipped.
- **An unknown key in a listing** is ignored, without an issue, so a misspelt field such as `colours` does nothing.
- **An incompatible options object** (such as a listing at the root rather than in the `listings` field) is reported.

An issue's `path` follows what you wrote: a field in the second map of an array is at `['listings', 1, 'plus', 'displayName']`, and one in a fragment definition's own listing at `['fragments', 'priceWithTax', 'listing', 'displayName']`.

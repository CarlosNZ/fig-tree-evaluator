Stage 00

The thing we actually want

Start with the situation, not the software. You are building an application whose behaviour has to be configurable by people who are not you: which form fields show, when a field is required, what a status badge says, which approver a request routes to. These rules change often, they differ per customer, and they are edited by administrators long after you have stopped looking at the code.

So the rules cannot live in the code. They have to live in data — a database row, a JSON file — where they can be edited, versioned and shipped without a deploy.

But rules are not static values. "Required if the applicant is under 18 and the country is not New Zealand" is a computation. So we need a way to store a computation as data, and later run it against whatever the situation is.

The obvious move — store a snippet of JavaScript and eval it — is out, and it is worth being precise about why, because those reasons shape everything that follows:

  • It is a code-execution hole. Anything that can write to that database row owns your server.
  • It cannot be inspected. You cannot ask a string of JavaScript "which data fields do you read?" or "is this still valid after I renamed that field?" without running it.
  • It cannot be edited safely by a non-programmer. There is no way to build a form-based editor over arbitrary code, and no way to tell an administrator what they broke before it breaks.

Which gives the shape of the thing we want: a computation expressed as ordinary data — JSON, storable, diffable, shippable — that a library can evaluate with no code execution at all, and that a tool can read, describe and check without running it.

That is the entire premise. Everything else in this document is the consequence of taking it seriously.

in the codeThe library is fig-tree-evaluator. An expression is JSON; the evaluator never calls eval, new Function, or anything equivalent.

Stage 01

The twenty-line evaluator

Represent a computation as a nested object: an operation name plus its arguments, where an argument may itself be an operation.

{ operator: 'greaterThan',
  values: [ { operator: 'plus', values: ['$data.order.total', '$data.order.shipping'] },
            100 ] }

Two conventions are doing work there. An object with an operator key is an operation. A string beginning $data. is a request to look something up in whatever data we are evaluating against, rather than the literal text.

Now the evaluator, in full:

function evaluate(thing, data) {
  if (isOperation(thing)) {
    const args = evaluateEachArgument(thing, data)   // recurse
    return operators[thing.operator](args)
  }
  if (isReference(thing)) return lookUp(thing, data)
  if (Array.isArray(thing)) return thing.map(x => evaluate(x, data))
  if (isObject(thing)) return mapValues(thing, x => evaluate(x, data))
  return thing                                        // a plain value
}

This works. It is recursive, it is short, and for a long time it is the right answer. Version 2 of this library was, in essence, this — and it ran in production for years.

So every complication after this point has to earn its place by naming a problem this version genuinely has. That is the discipline for the rest of the document: no mechanism without a wound.

in the codeThe v2 engine is still in the repo at /v2-src, kept runnable as a reference and as the oracle for the v3 test corpus.

Stage 02

Recognition is the hidden cost

The problem

Look at what the twenty-line version spends its time on. Before it can do any arithmetic, it must work out what each piece of the input is. Is this object an operation, or is it just an object? Is plus a real operation, or a typo? Is '$data.total' a reference, or a string that happens to start with a dollar sign? Does this operation spell its arguments the long way ({ operator: 'plus', values: [...] }) or the short way ({ $plus: [...] })? Is + an alias for plus?

Call that work recognition: deciding what each value in the document means, as opposed to computing anything. It is proportional to the size of the whole document, and — this is the important part — the twenty-line evaluator does it again on every evaluation.

Now look at how these expressions are actually used. The dominant pattern is one configuration object evaluated over and over against changing data: a form being re-validated on every keystroke, a page of fifty fields whose visibility rules all re-run when one answer changes, a list of a thousand rows each rendering the same template. The configuration is fixed. Only the data moves.

So we are re-deciding "is this an operation?" for two thousand values, hundreds of times, and getting the same answer every time. The recognition is pure waste after the first pass.

The idea

Separate recognising from computing. Walk the input once, decide everything decidable, and write the answers down. Then evaluate by reading the notes instead of re-interrogating the input.

What goes in the notes, for each piece of the document:

  • What kind of thing it is — a plain value, a data reference, an operation, a piece of structure.
  • If it is an operation: which one, resolved through aliases and spellings to a single canonical name, with each argument stored under the name the operation actually uses, whatever spelling the author chose.
  • If it is a reference: the path it reads, already parsed into segments.
  • Where it came from — its position in the document as the author wrote it, so we can point at it later.

This is the single most consequential decision in the design, and everything downstream is a consequence of it: once the notes exist, all sorts of things become cheap that were previously impossible.

What it costs

One extra pass over the input, once. A second representation to keep in sync with the first. And a new obligation: the notes are only useful if they stay valid, which we have to think about — that is stage 04.

in the codeThe notes are the parse artifact. The one-pass walk that builds it is parseExpression() in src/parse/parse.ts; the resulting shape is ParseArtifact in src/parse/artifact.ts. Each recognised piece is a compiled node, and there are six kinds: constant, reference, operator, fragment call, skeleton, invalid.

Stage 03

Most of a config is not logic

The problem

Real configurations are not expressions with a bit of structure around them. They are large structures with a little logic sprinkled in. A page definition might be two thousand lines of titles, labels, orderings and layout hints, with nine dynamic values in it.

The twenty-line evaluator treats that document as one giant expression: it walks all two thousand lines, copying every title and label into a new object, in order to discover that only nine positions actually needed computing. Every single time.

The idea

While recognising, also record what is constant. A piece of the document is constant if it contains no operation and no reference anywhere inside it — nothing that could produce a different answer on a different day.

That lets us split any structure into two things:

The middle one is a mould: the constant shape, with the dynamic positions left empty rather than filled. Alongside it we keep a list of those empty positions, each paired with the recognised operation that belongs there.

Now evaluation costs the number of dynamic positions, not the size of the document. Nine values get computed; the other two thousand lines are copied structure that was already decided. A document with no dynamic positions does not get evaluated at all — it is returned exactly as it came in.

Two details fall straight out of this, and both matter later:

The empty position must be distinguishable from an authored null. If the mould filled dynamic slots with null as a placeholder, we could no longer tell "compute something here" from "the author wrote null here". So the slot is left genuinely absent — an unassigned array index, a missing object key.

The mould must never be written to. It belongs to the notes, and the notes are reused by every future evaluation of that expression. If evaluation filled the mould in place, the second evaluation would inherit the first one's answers. So evaluation fills a copy of the mould, and the mould itself is permanently read-only.

What it costs

A second concept — mould plus filled copy — and a contract the caller has to respect. We deliberately do not deep-clone everything on the way out: the whole point was to stop touching two thousand lines per evaluation, and a deep clone per call would hand that cost straight back. So a result may share structure with the notes and with your original input, and the documented rule is that results are read-only. Mutate one and you corrupt the next evaluation. That was a deliberate trade, chosen over three heavier alternatives (clone everything, freeze everything, copy-on-write).

in the codeThe mould is the skeleton, an empty position is a hole, and a structure carrying both is a skeleton node — renamed from template in September 2026, because buildString.template already had the word. A structure with no holes collapses to a constant node and is returned by identity. The read-only rule is the "Result immutability" ruling in docs-dev/v3-specs/v3-evaluator-methods.md.

Stage 04

When are the notes still true?

The problem

Notes are only worth keeping if we know when they expire. So: what could change that would make a recognition decision wrong?

Recognition asked questions like "is $foo an operation, or inert data?" — and the answer depends on which operations are registered. Register a foo operation and the same document means something different. That is a real dependency.

What about the data? If any recognition decision depended on the data, the notes could not be reused across evaluations with different data — which was the whole purpose. So the notes must be data-independent, by construction, not by luck.

Same for settings. If the notes baked in "the maximum allowed depth is 20", then changing that setting per call would silently use stale notes. So the notes must also be setting-independent — with the exception of the handful of settings that define the vocabulary itself.

The idea

State it as a rule and hold to it: the notes may depend on the registered vocabulary and nothing else. Three settings define that vocabulary — the registered operations, the registered reusable snippets, and the per-instance default arguments for operations. Change any of those and the notes are discarded. Nothing else invalidates them, ever.

Anything genuinely setting-dependent is therefore kept out of the notes and computed per call instead. "Is this expression deeper than the limit?" is answered by storing the measured depth in the notes and comparing it to the limit at call time. Same for "does the sample data contain the paths this expression reads?" — the notes carry the list of paths; the comparison happens per call.

And now the notes can be cached. Two layers, each for a real usage pattern:

  • Keyed by object identity. The same configuration object, evaluated repeatedly — a form re-validating per keystroke. Looking that up is a pointer comparison, which is as cheap as it gets.
  • Keyed by content, behind it. Hosts that rebuild the object each time — a React component recreating it every render, a server loading fresh objects per request — would miss on identity forever. So a second, bounded layer hashes the serialized input; a hit re-registers the notes under the new object's identity, so that host pays one hash and is back to pointer speed.

Content-keying alone would not do, for two reasons worth knowing: it costs a full serialize on every call, which throws away the cost model from stage 03; and it is unsafe for expressions containing values that do not survive serialization — a function, a Date, a Map — because two different expressions can serialize identically and you would splice one's values into the other. Those expressions are flagged during recognition and served only from the identity layer.

What it costs

A discipline that has to be actively maintained — every new feature has to be checked against "does this smuggle a setting or a piece of data into the notes?" — and a second contract for the caller: do not mutate an expression object after evaluating it, because the identity cache will hand back notes describing the old shape.

in the codeThe three invalidators are operators, fragments and operatorDefaults. The unsafe-to-hash flag is identityOnly. The cache is designed but not yet built — it is Phase 8.2, and the seam it wraps is the parseExpression call inside FigTree.validate().

Stage 05

Finding mistakes before 2am

The problem

Go back to who writes these expressions: an administrator, in a web form, editing a rule that will run inside somebody's form submission next Tuesday. When they mistype an operation name or forget a required argument, the twenty-line evaluator finds out at the worst possible moment — mid-request, in production, in front of a user.

What we want instead is to find it when they press Save. But at Save time there is no data to evaluate against, and no user whose request we could make network calls for. So we cannot simply run the expression to see if it works.

The idea

Notice what the notes already contain. Recognition had to resolve every operation name, match up every argument, and parse every reference. That means an enormous amount is already known without any data at all:

  • an operation name that matches nothing registered — and, since we have the list, the nearest name we can suggest instead;
  • a required argument that was never supplied;
  • an argument key the operation does not have (a typo like thn for then);
  • a literal value of the wrong type — 'not a number' handed to something that needs a number;
  • a reference to a named value that is never defined anywhere in its scope;
  • an operation whose result type could never satisfy the argument it feeds — a yes/no value flowing into a position that only accepts numbers;
  • things that are legal but pointless, worth a warning rather than an error: a name defined and never used, a $something that resolves to nothing and will silently pass through as text.

So expose exactly that: a check-only mode that runs recognition and returns the list of findings, with no evaluation, no data and no network. It is almost free, because recognition was happening anyway — and it draws the line the whole design rests on: everything knowable without data is reported at authoring time; only the genuinely data-dependent failures wait for runtime.

Two practical wrinkles, and both shape the code:

The checking naturally splits in two. Some findings are about shape — this is not a well-formed operation at all, two operations in one object, an operator key whose value is not a string. Those have to be caught during the walk, because there is nothing coherent to inspect afterwards. The rest are about meaning — does this operation accept these arguments, of these types — and those need the whole operation assembled first, so they run as a second pass over the finished notes. The second pass is also much cheaper than it sounds, because it never descends into anything already marked constant.

Two passes must produce one ordered list. A reader expects findings in the order things appear in their document, not grouped by which internal pass found them. So every piece of the notes is stamped with a position number as the walk reaches it — parents before children — and both passes attach that number to their findings. Sorting at the end reconstructs document order.

And one invariant that this stage forces on everything: a broken expression must never crash the checker. If a malformed piece of input threw, an editor could not show the author what is wrong. So recognition never throws on expression content — a malformed piece becomes a placeholder marked invalid, an error finding is recorded, and the walk carries on to find the author's other mistakes too.

What it costs

Two passes to maintain rather than one, and a rule that every check must know which side of the data line it lives on.

in the codeCheck-only mode is fig.validate(). The shape pass is inside parse.ts; the meaning pass is runStaticChecks() in src/parse/staticChecks.ts. The position number is order, a finding is an Issue, and the placeholder is an invalid node.

Stage 06

Not every argument should be computed

The problem

The twenty-line evaluator computes every argument before calling the operation. For plus that is correct. For if it is wrong — and not merely wasteful:

{ $if: [ isAdmin, deleteEverything, doNothing ] }

Computing all three arguments runs both branches. If a branch makes a network call, you made it needlessly. If a branch fails, you get a failure from a branch that was never taken. Worse in practice: a branch that reads a field which only exists in the other case will blow up on data that is perfectly valid.

The same shape recurs everywhere once you look: a fallback value that should only be computed if the main thing failed; "the first of these that works", which must stop at the first success; a list of things where the same subexpression has to run once per element with a different element each time, which the eager rule cannot express at all.

The idea

Stop treating "compute the arguments, then call the operation" as a law. Let each operation declare, per argument, how it wants that argument delivered. Each kind of delivery exists because some operation cannot be written without it:

DeliveryMeansExists because
computed up frontthe value, already worked outthe common case — plus, comparisons
deferreda handle the operation chooses whether to forceif, and every "…or else this" default
first to finishseveral computed at once, settle earlyand / or: one false answer decides it
once per elementthe same subexpression run against each itemmap, filter, find
needed while readingmust be a fixed value in the document, not computedsee stage 07 — the engine itself has to read it

Now a second, larger consequence of declaring things. Once an operation states what arguments it takes, what types they accept, which are required and what it returns, that description is useful to three different readers:

  • the engine, to deliver arguments correctly and to check them at runtime;
  • the checker from stage 05, to do all its work centrally instead of each of forty operations hand-rolling its own validation — which is exactly how the previous version drifted, with every operation checking slightly differently and its documentation slowly diverging from its behaviour;
  • an editor, which can now offer a real form for an operation it has never heard of.

So the declaration is not bureaucracy; it is the single source of truth that makes stages 05 and 10 possible at all.

What it costs

Every operation is now a declaration plus a body, and the declaration has to be validated too — loudly, at registration, because a wrong declaration is a programming error, not a user error. It also means the engine, not the operation, owns argument handling: more machinery in the middle, less in each operation.

in the codeOperations are registered through defineOperator(), which validates the declaration and refuses to build a broken one. The delivery kinds are the evaluation modes: eager, lazy, race, perElement, structural. src/dev/demoOperators.ts has small worked examples of each.

Stage 07

Reaching the data, and naming things

The problem

An expression needs to reach into the data it is evaluated against, and JSON gives us no syntax to invent. We only have objects, arrays, strings, numbers, booleans and null. Everything expressive has to be encoded in one of those.

Strings are the only practical carrier for "read this field", so a marked string it is: '$data.user.name'. Which immediately raises the question a marked string always raises — what about text that legitimately starts with the marker? And then two harder problems:

Repetition. If the same subexpression appears three times in one rule, writing it three times means computing it three times, and editing it in three places.

Nesting. Inside a list operation, the current element needs a name. Inside a list within a list, both elements need names — and if the inner one simply shadows the outer, the outer one is unreachable.

The idea

For references: a precise rule rather than a guess. A string is a reference only if it starts with $ followed by one of a small fixed set of words, ended by the string or by . or [. So '$data.x' is a reference, '$5 off' is text, and '$notAThing' is text — though the author probably meant something, so it earns a warning rather than silence. Recognition resolves the path once, into segments, and records which data paths the expression reads. That list is then free to reuse: it is how "your sample data is missing a field this expression needs" gets answered without evaluating.

For repetition: let a node define named local values for its subtree. Each is computed at most once, the first time something asks for it, and not at all if nothing does.

For nesting: let a list operation rename its element binding — say the name is order, and inside that subtree the element is $order and its position $orderIndex. An inner list picks a different name, and both remain reachable.

That rename is where an interesting constraint appears, and it explains the fifth delivery kind from stage 06. To recognise '$order' as a reference rather than text, the reader — recognition, running long before any data exists — must already know that the name order is in play. Which means the rename cannot itself be computed: it has to be a fixed string sitting in the document. Hence a delivery kind meaning "the engine reads this while parsing", and hence a rule in the walk: read the rename first, then walk the per-element subtree with that name in scope, then drop it again on the way out.

What it costs

Recognition is no longer purely local — a string's meaning can depend on an enclosing rename, so the walk has to carry a small scope stack. That is the one piece of scope handling that cannot be deferred to the later checking pass, and it is why it lives in the walk.

in the codeReferences are $data (aliasable to $d), $vars, $params, $element, $index; the rule is in src/parse/references.ts. Named local values are vars. The rename is the as parameter, declared structural.

Stage 08

Absence, failure, and being cut off

The problem

These expressions read from databases and HTTP endpoints, against data assembled from user input. Things will be missing and things will break, and the twenty-line evaluator's answer to both is the same: throw. That is too blunt, in two directions.

First, a missing field is usually not an error. An applicant with no middle name is not a failure; it is an applicant with no middle name. If absence throws, every optional field needs defensive ceremony and the whole config becomes noise.

Second, some failures are expected and should be designed for. If a currency API is down, a dashboard should show a stale rate or a dash, not a blank page.

And a third problem specific to what we are building: if evaluation is cut off by a deadline — the whole thing has a timeout, because one hanging HTTP call should not hold a request forever — what do we return? Half an object is worse than nothing.

The idea

Separate absence from failure. A missing field resolves to nothing — null — and carries on. Failure is a distinct category, raised only when something genuinely went wrong: an operation that cannot do its job, a request that errored, a division by zero.

Give any node a safety net. A node may carry a value to use if it fails. Reach for it and the failure is handled, as the author designed — not silently swallowed, because it is still recorded for anyone who asks what happened.

Then the deadline problem, which has a neat answer once the notes exist. Remember that every dynamic position in the document is known ahead of time, and so is whether its safety net is a plain constant. So during recognition, work out one fact per dynamic position — could this position be filled without evaluating anything? — and one fact for the document as a whole: do all of them have that property?

If they do, a timeout is no longer a disaster. Take the mould, splice in whatever finished in time, use the constant safety nets for the rest, and return a complete, correctly-shaped answer with no evaluation after the deadline. If they do not, the deadline has to be an error, because there is nothing honest to return.

That single fact is worth surfacing to the author, too: an editor can show it as a badge — this expression is guaranteed to produce something — which turns a runtime property into something you can see while writing.

One more thing failure needs: a location. "Cannot divide by zero" is useless on its own. So every piece of the notes remembers where it came from in the document as the author wrote it — not where it ended up after aliases and shorthand were normalised away — and errors carry both the failing spot and the dynamic position it belonged to.

What it costs

Two more things precomputed into the notes (which is why per-instance argument defaults invalidate them — a default safety net changes the answer), and an extra concept for the author to learn.

in the codeThe safety net is fallback. The precomputed facts are each hole's staticFallback and the artifact-level shielded flag, surfaced as timeoutShielded. Failures are FigTreeError, carrying path and holePath.

Stage 09

The same work twice

The problem

A page configuration might reference the same exchange rate in four places, or ask the same database question for every row in a list. The notes cache from stage 04 does nothing for this: that one avoids re-recognising the document. This is about not re-doing the same work within or across evaluations.

The idea

A second cache, and it has to be second because it keys on something completely different. The notes cache keys on what the author wrote, before any data exists. This one keys on what actually got computed — an operation plus its resolved arguments, or for a network call, the request as finally assembled.

The cross-cases show why one cache could never serve both. One expression evaluated against two different data sets shares its notes but must not share results. Two differently-written expressions that assemble the same HTTP request should share the result but have different notes. Their lifetimes differ accordingly: notes are dropped only when the vocabulary changes, whereas results need expiry, a size bound and a pluggable store, because they are about the outside world.

There is one honest synergy, and it is only about assembling keys, not sharing them: since recognition already knows which arguments are fixed, it can pre-build most of a result key at parse time, leaving evaluation to slot in the parts that vary.

in the codePer-node result caching is the useCache option and the cache store; the pre-built key is the artifact's precomputed slot. Phase 9.

Stage 10

The editor comes free

The problem

Back to stage 00: these expressions are edited by people who are not programmers. That needs a real editor — one that offers the available operations, shows what arguments each takes, and says what is wrong with the current draft. If building that editor requires the engine to grow a parallel description of itself, the two will drift apart, and the editor will confidently describe behaviour the engine no longer has.

The idea

Nothing new is required. The pieces are already there for other reasons:

  • What operations exist and what they accept — the declarations from stage 06, exposed for reading.
  • What is wrong with this draft — check-only mode from stage 05, which needs no data and no network, so it can run on every keystroke in a browser.
  • Will this survive a timeout — the precomputed fact from stage 08.
  • Which data fields does this touch — the path list from stage 07, which also answers "will this still work if I rename that field".

This is the real dividend of doing recognition once and writing it down. Three quite different products — evaluation, authoring-time checking, and an editing UI — turn out to be three views over one artifact, rather than three implementations that must be kept in agreement.

in the codegetOperators() reports the declarations; the editor itself lives in a separate package, fig-tree-editor-react. Some exports in src/index.ts exist only for it.

Stage 11

The model, assembled

Everything above collapses into three stages with a strict division of knowledge. That division is the model.

1 · Recognise

Knows: the document, the registered vocabulary.

Never knows: the data, the per-call settings.

Produces: the notes — a tree of recognised pieces, the list of dynamic positions, the moulds, the findings, the precomputed facts.

2 · Check

Knows: the notes, the declarations.

Never knows: the data.

Produces: more findings, merged into document order with the first stage's.

3 · Evaluate

Knows: the notes, the data, the settings.

Adds: nothing to the notes — it only reads them.

Produces: the answer, filled into copies of the moulds.

Stages 1 and 2 run once per document and are cached. Stage 3 runs per evaluation and costs the dynamic positions, not the document. Stages 1 and 2 together are what check-only mode exposes; all three are what evaluation does.

The six kinds of recognised piece

The vocabulary of the notes, which is just the list of distinct things recognition can conclude:

KindMeansAt evaluation
constantnothing inside can varyreturned as-is, untouched
referenceread this path out of the datalooked up
operatorthis operation, these argumentsarguments delivered per declaration, then the body runs
skeletonconstant structure with dynamic positionscopy the mould, fill the positions
fragment calla reusable expression, invokedits pre-recognised body is spliced in
invalidmalformed — the finding is already recordednever reached; evaluation refused earlier

The invariants

  • Recognition never throws on document content. Every malformed thing becomes a finding plus a placeholder, so an editor can always show the author everything that is wrong.
  • The notes are immutable and reusable. No data in them, no per-call settings in them, never written to during evaluation.
  • The input is never modified. Results may share structure with it; nobody rewrites it.
  • Recognition happens exactly once, in one place. No value is re-interpreted at evaluation, and data that arrives at runtime is never re-read as an expression — a string that looks like a reference but came from the database is just a string.
  • Absence is not failure. Missing resolves to nothing and carries on; failure is its own category with its own handling.

Stage 12

One expression, end to end

A small configuration with a three-deep computation inside it:

{ label: 'Shipping',
  message: { operator: 'if',
    condition: { '$>': [ { $plus: ['$data.order.total', '$data.order.shipping'] }, 100 ] },
    then: 'Free shipping',
    else: { $format: ['Standard: %1', '$data.order.total'] } } }

After recognition

Printed by the repo's dev inspector. Each line is one recognised piece; #n is its position number and the right-hand column is where it sits in the document as authored.

skeleton  1 hole  shape: {"label":"Shipping","message":<hole>}   #0  (root)
  at message: operator  if                                        #2  message
    condition: operator  greaterThan                              #3  message.condition
      values: skeleton  1 hole  shape: [<hole>,100]                #4  message.condition.$>
        at [0]: operator  plus                                    #5  message.condition.$>[0]
          values: skeleton  2 holes  shape: [<hole>,<hole>]         #6  …$plus
            at [0]: reference $data.order.total                   #7  …$plus[0]
            at [1]: reference $data.order.shipping                #8  …$plus[1]
    then: constant  "Free shipping"                               #10  message.then
    else: operator  format                                        #11  message.else
      template: constant  "Standard: %1"                          #12  …$format[0]
      substitutions: skeleton  1 hole  shape: [<hole>]             #13  message.else.$format
        at [0]: reference $data.order.total                       #14  …$format[1]

dynamic positions: 1  →  message
reads: order.total, order.shipping     survives a timeout: no

Things to notice, because each one is a stage above doing its job. The shorthand $> and the alias > are gone — the operation is greaterThan, and its positional arguments now sit under the name it declared, values (stage 02). The whole document has exactly one dynamic position, message; the label is constant structure (stage 03). The moulds show reserved slots as <hole>, distinct from a written null (stage 03). The reads are listed (stage 07). The timeout answer is "no", because that if has no constant safety net (stage 08).

Then checking

The second pass walks those pieces and finds nothing here: 100 and 'Standard: %1' satisfy their declared types, nothing required is missing, no name is unresolved, and greaterThan's two-argument constraint is met. Had the author typed thn:, or handed a yes/no value to something needing a number, this is where it would surface — with the document position of the mistake, before any data existed.

Then evaluation, against { order: { total: 80, shipping: 15 } }

  1. The root is a mould with one position. Copy { label: 'Shipping' }; the label is never computed, it is already an answer.
  2. Fill the message position: that is the if. Its declaration says the condition is computed up front and both branches are deferred — so only the condition runs now.
  3. greaterThan's argument list is a mould: copy [·, 100], fill position 0 by evaluating plus.
  4. plus's argument list is a mould too: copy [·, ·], fill both by reading the data — 80 and 15 — giving [80, 15], which the body turns into 95.
  5. 95 fills the reserved slot: [95, 100] → the body answers false.
  6. if forces exactly one deferred branch — the else. The then branch is never computed, though it was recognised and checked.
  7. format's substitutions are a mould: copy [·], fill by reading the data → [80] → 'Standard: 80'.
  8. That fills the reserved message key: { label: 'Shipping', message: 'Standard: 80' }.

Read that list again and two things stand out. Every mould filled along the way except the last one is an argument list, not output — only the outermost is the shape of the answer. And control ran downwards while values came back upwards: a parent cannot finish until the children it actually asked for have finished. Where a template has several positions, they are filled concurrently, so "upwards" describes the dependency order, not a serial sweep.

What exists today

Stages 1 and 2 are built and tested: recognition, the notes, the moulds, both checking passes, and check-only mode. Stage 3 is designed in detail and not yet written — there is no evaluate() in v3 yet, and the caches of stages 04 and 09 come with it. The evaluation walkthrough above is therefore the design, not observed behaviour; everything before it is real output.

Stage 13

What it cost

An honest ledger, since every stage above added something.

A cost on the very first call. Recognition is real work — measured on this repo, roughly half a microsecond per piece of document, so about 2.5 ms for a five-thousand-piece expression, and about 2 µs for a small one. For an expression evaluated once, that work is not repaid by any cache; it is repaid only by the fact that the old evaluator did the same recognition inline, on every evaluation. The case that could genuinely lose is a tiny expression evaluated exactly once, and that is on the list to be measured against the old engine before release rather than assumed away.

Two contracts the caller has to keep. Do not modify a result; do not modify an expression object after evaluating it. Both are documentation, not enforcement — the alternatives all cost more than the bug they prevent.

Caches belong to an instance. The notes bake in a particular registered vocabulary, so they cannot be shared between instances with different vocabularies. Which makes one long-lived evaluator the intended pattern, and a fresh evaluator per request the way to get no caching at all.

More machinery in the middle. The engine now owns argument delivery, type checking, absence handling and failure handling, so each operation is smaller but the engine is bigger. That was the explicit trade: the previous version's forty-odd operations each did their own checking, and drifted.

Everything is asynchronous. Once an operation may make a network call, and arguments may be deferred or raced, a synchronous path would be a second engine rather than a flag. There is no synchronous evaluation.

Two representations to keep honest. The notes are derived from the document, and every future feature has to be checked against the division of knowledge in stage 11 — is this fact allowed in the notes, or does it depend on data or settings? Get that wrong and you get stale results that are very hard to diagnose.

The one-paragraph version

Store logic as data so it can be edited, shipped and inspected without running code. Interrogate that data once to find out what everything means, and write the answers down. The answers reveal that most of a document is constant, so keep the constant shape whole and remember only the positions that need filling — which makes evaluating a large configuration cost its handful of dynamic values rather than its size. The same answers reveal almost every authoring mistake without any data at all, so hand those back at authoring time instead of at 2am. Let each operation declare how it wants its arguments so that branches which should not run do not run, and so that one central description serves the engine, the checker and the editor at once. Keep the answers strictly free of data and settings so they can be reused for the lifetime of the document, and precompute from them the one fact — can every dynamic position be filled without computing anything — that lets a timed-out evaluation still return a complete answer.

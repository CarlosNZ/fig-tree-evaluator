# FigTree v3 — implementation notes

_Non-binding. This doc captures **suggested mechanisms** raised during the design discussions so they aren't lost by implementation time. The contract lives in [v3-api.md](v3-api.md); if an idea here turns out to conflict with the spec, the spec wins. Nothing in this file is agreed API._

## Deep evaluation without a runtime traversal cost

The spec makes deep evaluation the only semantics ([v3-api.md → Deep evaluation](v3-api.md#deep-evaluation)). The naive reading — walk the whole input on every `evaluate()` call looking for nodes — is exactly what v2's `evaluateFullObject` does ([evaluate.ts:59](../../v2-src/evaluate.ts#L59)), and it re-pays the full traversal on every evaluation. The suggested v3 mechanism moves all recognition to a one-time parse so the per-evaluation cost is proportional to the number of _evaluable_ nodes, not the size of the input.

### Parse → compile → evaluate

1. **Parse/normalize once.** A single walk over the raw input normalizes shorthand faces and symbolic/namespace aliases to canonical form, recognizes reference strings, runs structural validation (`maxDepth` / `maxNodes`, unknown-`operator` hard errors, unresolved-`$` warnings), and classifies every subtree. This is the same pass the spec already requires for "shorthand normalizes once, at parse" — deep recognition adds no extra traversal, just one more question asked per node.

2. **Classify subtrees bottom-up.** During that walk, mark each subtree **constant** iff it contains no operator/fragment/function node and no reference string (and everything inside `literal` is constant by fiat, unwalked). The flag is free to compute: a node is constant iff all its children are constant and the node itself isn't evaluable.

3. **Compile plain literals to constants-with-holes.** A plain object/array literal containing evaluable descendants compiles to a _skeleton node_: the constant skeleton plus a list of `(path, compiledNode)` holes (the kind was called `template` until September 2026 — renamed to end the collision with `buildString.template`). Evaluating the literal = evaluate all holes (concurrently, the way `evaluateArray` already works in v2) and splice the results into a copy of the skeleton. A literal with zero holes — the fully-constant case — evaluates as **identity**: return it as-is without touching it.

4. **Cache the compiled form.** Key the parse cache on input identity (`WeakMap` keyed on the object reference) with a fallback path for fresh/serialized inputs. The dominant real-world pattern (Conforma) is the same config object evaluated many times against different `data` — after the first call, every subsequent evaluation skips recognition entirely. This is also why the spec forbids per-call `operators` and `fragments`: the compiled form bakes in registry resolution (which `$key`s invoke, which are inert), so the parse cache is only sound against a stable registry — and why an `updateOptions()` call that changes the invocable registry must invalidate the parse cache.

### Cost model

| Work                                                    | When                    | Proportional to                   |
| ------------------------------------------------------- | ----------------------- | --------------------------------- |
| Recognition, normalization, validation, hole extraction | once per distinct input | input size                        |
| Per-evaluation work                                     | every call              | number of holes (evaluable nodes) |
| Fully-constant subtree                                  | every call              | O(1) — identity                   |

### Subtleties to resolve at implementation

- **Result sharing / immutability.** The identity short-circuit and skeleton splicing both return objects that share structure with the cached compiled form (and therefore with other results, and with the caller's original input). A caller mutating a result would corrupt future evaluations. Options: deep-freeze the cached skeleton and document results as immutable; copy-on-write only along hole paths (shares constant subtrees — fast, but mutation still leaks); or `structuredClone` the skeleton per evaluation (safe, still much cheaper than re-walking with recognition logic, but no longer O(holes)). Not decided here — deferred to the Evaluator-methods area in the spec.
- **Error paths and trace come free.** The hole list carries each evaluable node's path in the input, which is exactly the path `FigTreeError` must be tagged with for `mode: 'report'` and editor diagnostics. One compile artifact serves both features.
- **Per-evaluation context.** Hole evaluation threads the same frozen per-evaluation context (merged options/data, `vars` scope chain, abort signal) as any other node evaluation; a literal's holes are siblings for concurrency purposes, like array elements.
- **`literal` boundaries.** `literal` contents must be excluded at _parse_ (never walked, never validated), not merely skipped at evaluation — otherwise `maxNodes`/unknown-operator checks would fire inside quoted data.
- **Cache keying for non-identical inputs — a two-layer parse cache, designed in from the start.** Originally parked here as "measure before adding"; upgraded at the Evaluator-methods review (Carl, July 2026) because the dominant deployment patterns _are_ the measurement: React hosts re-create expression instances render to render, and back-end hosts load fresh instances per request (the same validation expressions arriving twenty times in twenty submissions). Shape: the identity `WeakMap` in front, a **bounded content-keyed LRU behind it** (key: the serialized input itself; bounded because it holds strong references; internal default size, no option until demand). _Amended at Phase-8.2 implementation (Carl, September 2026): the key is the serialized string, **not a hash of it**. Hashing does not replace serialization, it follows it, so it is strictly more work at both insert and lookup — and a `Map` keyed on a string already hashes natively and then verifies with full equality, where a hand-rolled digest would replace a verified hash with an unverified one whose collision serves the wrong artifact, silently. All a hash buys is a smaller retained key, which the bound already bounds. *Premise corrected September 2026 by the content-layer measurement below: "strictly more work at both insert and lookup" does not hold as stated, because the `Map` re-hashes the full key on every lookup anyway. Below V8's `kMaxHashCalcLength` (16383 characters) that native hash runs at **1.16 ns/char** and is the **larger half of a hit**, against the serializer's own 0.2–0.5 ns/char; above it V8 substitutes a length-derived hash and the lookup drops to 0.02 ns/char. So a short digest, with the full serialized string retained in the entry and compared on a bucket match, would keep the verified-equality property fully intact and roughly halve the sub-16 KB hit. The ruling stands — the lever is not worth pulling at the measured absolute costs — but it stands on the collision argument alone, not on this one.* The serializer is **not `JSON.stringify`** either: that throws on a cycle, honours `toJSON`, drops `undefined` and functions, and flattens `NaN`/`±Infinity`/`-0`/`Date`/`Map` — each of which either crashes the lookup or lets two different inputs share a key. It is a self-delimiting, length-prefixed grammar that **refuses** anything non-plain (src/parse/contentKey.ts), and the refusal is the non-plain-value guard named below._ A content hit re-registers the artifact under the new instance's identity, so a fresh instance pays one serialize+hash and is O(1) thereafter. **Why not content-only** (asked and answered at review): content keying costs an O(input) serialize on _every_ call, which silently breaks the O(holes) per-evaluation promise this whole mechanism exists for — the motivating workload is a large config with few holes evaluated rapidly (form re-validation per keystroke), where identity is a pointer lookup; and identity is the _only_ possible caching for expressions containing opaque constants — functions, class instances and `Map`s vanish or flatten under JSON serialization, so two different such expressions can serialize identically and a content hit would splice in the wrong constants (the key-building serializer flags non-plain values and marks such artifacts identity-only). The identity layer costs nothing to keep: no eviction, no bound, entries die with their keys. Mutation self-corrects in the content layer (changed bytes → honest miss) but not the identity layer — the don't-mutate contract line stands; key-order differences between semantically equal inputs are harmless misses, deliberately not canonicalized. Worst case (all layers miss, recompile per call) is still roughly v2's baseline, which re-walks the input every evaluation. The structure is **per instance** (artifacts bake in registry resolution) — the intended pattern is a module-level singleton `FigTree`, which is established practice (and what the result cache wants anyway).
- **Parse-cache sizing and eligibility — measured September 2026** (on the real Phase-3 parser, artifacts held live, forced GC between samples). Per-artifact cost: **~4.2 KB and ~3.1 µs** for a form-shaped expression (4 operators, a few references), **~400 B and ~200 ns** for a purely static value; the figure tracks _evaluable_ nodes, not input size — one 2,000-field mostly-constant config is 158 KB of JSON and only 216 KB of artifact (1.4×), because constant subtrees collapse to single nodes that share the input's objects. Working-set sizing from Conforma (Carl): **up to 500 expressions**, normally fewer. So the content layer wants a bound in the low hundreds — 500 × 4.2 KB ≈ 2.1 MB — and the retained figure is dominated by each node's own `path` array (the O(nodes × depth) allocation, retained as well as spent; parent pointers with lazily-built paths is the lever if it ever needs shrinking). **Eligibility matters more than the bound**, on two findings from the Conforma shape (~800 evaluable values per form, ~90% of them plain static values — labels, numbers, booleans): (a) a `WeakMap` cannot key a primitive, so the identity layer structurally _cannot_ hold those 90%, leaving them to hash through the content layer on every call; and (b) letting them into the content LRU would evict exactly the expressions that benefit from it. Both say the same thing for _primitives_. Constant **containers** split the other way, and the distinction matters (measured September 2026 on static options lists): a constant container collapses to one node holding the caller's array/object by reference, so its artifact is a flat **~400 B whatever its size** (5 entries or 200 — the per-child nodes are discarded at collapse), but _building_ it is O(size) — **4.5 µs for a 20-entry options list, 34 µs for 200**. So a constant container belongs in the identity layer (it is a legal `WeakMap` key, the layer costs nothing to keep, and a hit turns that O(size) walk into a pointer lookup) and stays out of the bounded content layer (parse costs only ~2.2× `JSON.stringify` on the same input, so a content lookup spends roughly half the price of just reparsing — a poor trade for an LRU slot and a strong reference). The rule, then: primitives skip both layers, constant containers take the identity layer only, expressions with holes take both. `holes.length === 0` plus a `typeof` test is the whole discrimination, and both are already to hand. _Amended at Phase-8.2 implementation (Carl, September 2026): this entry predates the constancy probe below, and under the probe `evaluate()` never builds an artifact for a constant container at all — so there would be nothing to put in the identity layer. The layer therefore holds **either a compiled artifact or a memoized probe verdict** (with its measured depth, which is what `maxDepth` compares against), which is what makes "a hit turns that O(size) walk into a pointer lookup" true as written. It also settles where the verdict belongs: the probe consults the registry, so an operator registered later turns a previously-inert value into an expression, and living in the parse cache means the verdict is dropped by the same three options. A separate side map would have been an invalidation bug waiting to happen. The bound was set at **200**: the identity layer already carries the hot working set unbounded and free, so the content layer covers only fresh arrivals, and at ~4.2 KB per artifact plus its retained key that is about 1 MB. The inert memo has no observable semantics beyond the `maxDepth` carry-over — it is a performance property, pinned at Phase 16, not by a unit test._ Reassurance the measurement also bought: a full cold reparse of all 800 values costs **0.33 ms**, so for this workload the cache is a convenience, not a load-bearing requirement.
- **Content-layer cost against the compile it replaces — measured September 2026** (node 22, min-of-five rounds, reproducible via `pnpm dev parseCacheBench` — src/dev/parseCacheBench.ts). The question the sizing entry above leaves open: a content hit pays an O(input) serialize plus a string-keyed `Map` lookup _instead of_ the compile, so can it cost more than simply reparsing? **It can**, and the discriminator falls straight out of the two cost models — the compile tracks _evaluable nodes_ (a constant subtree collapses to one node holding the caller's value by reference, so bulk is nearly free), while the key tracks _input bytes_, every one serialized and then every one hashed again. **Static bytes per hole** is the whole of it. Three regimes, `hit / compile`:

  | shape                             | key      | nodes | hit       | compile   | ratio     |
  | --------------------------------- | -------- | ----- | --------- | --------- | --------- |
  | form-shaped (6 ops, refs)         | 0.2 KB   | 9     | 0.91 µs   | 5.59 µs   | **0.16×** |
  | 40 operator pairs, no constants   | 2.3 KB   | 160   | 12.92 µs  | 97.59 µs  | **0.13×** |
  | config: 20 sections, hole in 4    | 3.4 KB   | 20    | 12.68 µs  | 18.77 µs  | **0.68×** |
  | config: 100 sections, hole in 10  | 16.1 KB  | 40    | 37.42 µs  | 59.91 µs  | **0.62×** |
  | config: 500 sections, hole in 50  | 79.4 KB  | 40    | 170.41 µs | 207.81 µs | **0.82×** |
  | one hole + 200-entry options list | 9.1 KB   | 2     | 49.32 µs  | 48.14 µs  | **1.02×** |
  | one hole + 100 KB string          | 101.6 KB | 2     | 5.16 µs   | 0.93 µs   | **5.55×** |

  So: expression-dense inputs — what an editor actually emits — are a clean **6–8× win** and uncontroversial; mostly-static configs are a **win of only 1.2–1.6×**, much closer than the design assumed; and a large opaque payload behind a single hole **inverts**, to 5.5× and as far as 30× at 200 KB. Crossover, sweeping static text against a fixed hole count: **~600 static characters per hole** for a minimal expression, **~4,000** for a six-operator one. Spreading the same bytes over many short strings stays near break-even (0.72–0.86× from 20 KB to 200 KB) because then the parser must walk them too — it is one _large_ value, which the parser stores by reference in O(1), that breaks the symmetry.

  Two findings about the `Map` that the hit cost rides on, neither of them about this library. First, V8 content-hashes a string key only up to `kMaxHashCalcLength` (16383 characters) and substitutes a length-derived hash past it, so **cost is non-monotonic**: a 10 KB key costs 12.11 µs to look up and a 20 KB key 1.08 µs. Second, the tail of that — above the threshold, keys sharing a _length_ share a bucket: 200 same-length 20 KB keys measure **31.79 µs** per lookup against **0.48 µs** for distinct lengths, a 66× penalty. It needs 200 long expressions of exactly equal length to bite (a rendered list of structurally identical rows is how that would happen), so it is remote rather than theoretical.

  **Ruling: no engine change.** A byte budget in the serializer is nearly free to add — the refusal channel already exists, so aborting the walk past N characters is a few lines — but the measurement argues against it: any budget tight enough to catch the blob case also evicts the 100- and 500-section configs, where bailing out costs _more_ (a wasted partial serialize plus the full compile) than the modest win it gives up. Bytes-per-node is the honest discriminator and it is not knowable before serializing. The exposure is authoring guidance instead — hoist large static payloads (markdown, base64, long options lists) into `data` or behind `literal` rather than inlining them — and it is bounded anyway: the worst measured absolute cost is 28 µs on a 200 KB expression. One caveat worth carrying: in the fresh-object-per-render pattern the identity layer **never** hits, so whatever the content layer costs is paid on every render forever — fine at 0.16×, a standing tax at 5×.

- **Skip the parse for inert inputs — a recognition-only constancy probe (Phase-4 candidate; measured and argued September 2026, Carl's proposal).** The wound is the Conforma shape: ~800 evaluable values per form, ~90% of them plain static data (labels, numbers, booleans, options lists) which v2 returned untouched for a type check, and which v3 currently parses. The mechanism is _not_ `isEvaluable()` as specified — that is defined via the parse, so calling it saves nothing — but the allocation-free probe already in the tree as `isConstantValue` (parse.ts, written for `operatorDefaults` fallbacks): walk the raw value, bail at the first operator/fragment/reference found, allocate nothing. Measured: on inert values the probe replaces the parse at **3.6–10.6× cheaper** (static string 47 ns vs 502 ns; 20-entry options list 948 ns vs 4.1 µs; 200-entry 9.6 µs vs 34 µs); on real expressions it is near-free overhead because it bails immediately (**2%** of the parse for a canonical operator at the root, 12% for a shorthand); the one loser is a large mostly-constant config whose holes sit late — **+40%** on a cold parse (100-section config: probe 90 µs before a 225 µs parse). Net: a clear win for the config-with-mostly-static-values workload, and it removes the need for hosts to hand-wrap static containers in `literal` for speed. **Recommended unconditional, not an option** (contra the first sketch): a host that gates its own calls never passes inert values, so the probe costs it nothing, and a boolean that changes only performance buys a support surface and a test dimension with no behavioural choice behind it — add it later if a measured victim appears. Three things it needs settled at implementation: (1) the skip belongs to `evaluate()` only — an inert value can still earn the unrecognized-`$` warning, so `validate()` keeps parsing in full, and the skip should be off when `trace` is requested (a skipped parse has no nodes for the trace to echo); _`mode: 'report'` is the other half of that question and answers the other way (Phase-12 planning, September 2026): report needs no nodes, only an envelope, so it **keeps** the probe and wraps the identity return as `{ result: <the input>, errors: [] }` — and the one thing the inert path can still fail on, its `maxDepth` check, reports rather than throws like any other static error;_ (2) it is a _second_ answer to "is this evaluable?", the drift hazard this design refuses elsewhere — so `isConstantValue` must become the single shared implementation, with a property test asserting the probe agrees with the parser over a corpus, as a condition of shipping — _built as `probeConstant` (src/parse/probe.ts, Phase 4); the property is `probe(x).constant === (parse(x).root.kind === 'constant' && parse(x).root.value === x)`, stricter than `holes.length === 0`: a `//` key, a consumed `vars` block or an `undefined` value leaves zero holes yet normalizes the value, so the probe must refuse those too for the identity return to be honest (test/probe.test.ts)_; (3) `maxNodes` stops applying to inert inputs, which on inspection is **desirable** rather than a hole (an inert 10,000-node object costs nothing to evaluate and ~400 B to retain — the 601-node options list tripping a 500-node guard was a false positive); ruled September 2026 by narrowing `nodeCount` itself to _evaluable_ nodes (obligations B4, provisional) with a built-in mid-walk ceiling for walk cost, so the probe need not count at all — but depth must still be tracked and ceilinged during the descent, see the next entry. Bonus worth taking: **`isEvaluable()` should be respecified on the probe** rather than the parse, making it an allocation-free early-bailing scan — cheap enough for an editor to run per keystroke, which is what hosts actually want it for (amendment to "isEvaluable" in [v3-evaluator-methods.md](v3-evaluator-methods.md)).
- **`maxDepth` cannot currently do its job — enforce a structural ceiling inside the walk (bug found September 2026).** The recursive walk measures depth as it descends and the limit is compared _afterwards_, in `FigTree.validate()`. So a deep input dies in the walk before the comparison: with `maxDepth: 50` explicitly set, depth 1,000 reports `max-depth` correctly but **depth 1,500 throws `RangeError: Maximum call stack size exceeded`** (Node's default stack; a browser's is smaller). That breaks the specified invariant that `validate()` never throws on expression content, and it means the one rationale that clearly justifies a depth limit — stack safety, which applies to inert data exactly as much as to expressions — is the one thing the limit fails to deliver. Fix: a **built-in, option-independent ceiling enforced inside `walk()`** (conservative, ~500, since environments differ), emitting an error issue and refusing to descend further; the artifact stays option-independent because the ceiling is not an option, and the user's `maxDepth` remains the per-call check against the measured depth for hosts wanting something tighter. The constancy probe above must carry the same ceiling, since it recurses too.
- **Two caches, deliberately disjoint.** The parse cache (above) and the result cache (`useCache` / the `cache` option) key different worlds and cannot unify: parse keys the _authored input_ before any data exists and is data-independent; results key _resolved runtime values_ per node — operator + resolved parameters, or the effective request for I/O (ledger #16). The cross-cases prove the split: one expression against different data shares its artifact but forks result entries; two expressions spelling the same HTTP request fork artifacts but share one result entry. Lifetimes differ to match (parse: invalidated only by the registry-affecting options, no clearing API; results: pluggable store, TTL, `clearCache()`). One real synergy — key _assembly_, not key sharing: the artifact can precompute each cacheable node's result-key skeleton at parse (literal params serialized once; a fully-literal I/O node's effective-request key is entirely static), so per-evaluation key building splices dynamic slots instead of serializing from scratch. Micro-optimization, not a coupling — and, assessed September 2026, **almost certainly not to be built**: the skeleton rides one artifact (so a second expression spelling the same request gets no shortcut, though it still shares the result entry), and parse-time work is unconditional where evaluation is not, so it pays for every never-taken branch on the cold first call to save sub-milliseconds behind a network call. Full argument, and the side-table alternative that would keep the artifact immutable, in obligation 7 of [v3-artifact-obligations.md](v3-artifact-obligations.md).
- **The full invalidation set is `operators`, `fragments` — and `operatorDefaults`** (the third caught at the Evaluator-methods review, July 2026): reserved-modifier defaults (`plus: { fallback: 0 }`) count as the node carrying a static fallback for timeout shielding, and the shielding flags + per-hole static-fallback constants are precomputed into the compile artifact (see the shielding section below) — so an `updateOptions({ operatorDefaults })` must drop the parse cache or those classifications go stale. Nothing else invalidates: to keep it that way, the artifact is **option-independent** — option-dependent static checks aren't baked in (store the tree's measured depth/node count and compare against `maxDepth`/`maxNodes` per call; sample-data warnings walk the artifact's dependency list). Per-instance cache, since the artifact bakes in that instance's registry resolution. (`excludeOperators` removed from v3 — Options ruling, July 2026 — so no exclusion concern touches recognition or the cache.)

## Truthiness is one function

The spec defines FigTree truthiness once and marks the empty-container question for revisiting ([v3-api.md → Truthiness](v3-api.md#truthiness)). The implementation requirement that enables the revisit: a single shared `isTruthy(value)` consumed by _every_ truthiness site — `if.condition`, `and`/`or`/`not`, the `filter`/`find`/`some`/`every` predicates, and `convert`'s `to: 'boolean'` target (applied after the `"true"`/`"false"` string carve-out). No operator body re-implements the falsy check inline; refining the falsy set later must be a one-function change that applies globally.

## Ordering is one comparator; rounding is decimal-safe

Two more shared-function requirements from the parameter passes, with the same drift-proofing rationale as `isTruthy()`:

- **One ordering comparator.** The agreed relation (homogeneous `number` | `string` operands, plain codepoint order for strings — [v3-api.md → No implicit coercion](v3-api.md#no-implicit-coercion)) is implemented once and consumed by the four ordering comparisons (batch 2, parameterized by direction and inclusivity) and by `min` / `max` (batch 3, a fold over the same relation). No operator body re-implements `<`.
- **Decimal-representation rounding.** `round`'s half-away-from-zero ties (batch 3) can't be built on `Math.round` (which rounds half toward +∞, so `Math.round(-2.5)` → `-2`) nor on naive scale-multiply-round float arithmetic (`1.005 * 100` → `100.49999…`): the implementation shifts the decimal _representation_ (exponent-string manipulation or equivalent), so `round(1.005, 2)` → `1.01` and negative `decimals` shift the same way. The spec point is only that results match the decimal reading of the input, not float artifacts.

## Text rendering is one function

Same drift-proofing pattern again, from the `buildString` pass (batch 4): the stringification table ([v3-api.md → Stringification](v3-api.md#stringification-one-rendering-table)) is implemented as a single shared renderer consumed by `buildString` (token rendering), `join` (elements), `match` (branch-key comparison), and the scalar rows of `convert` `to: 'string'`. No operator body calls `String(x)` directly — v2's ad-hoc `String(sub)` calls are exactly where `"[object Object]"` leaked from ([STRING_SUBSTITUTION/operator.ts:55](../../v2-src/operators/STRING_SUBSTITUTION/operator.ts#L55)) — and the composite-value policy lives in this one function — `<array>` / `<object>` placeholders in rendering positions, a hard failure in `convert` (the one sanctioned fork, Type area).

## String primitives are shared functions too

Three more single-definition requirements from the batch-4 passes, same drift-proofing rationale as `isTruthy()`:

- **One whitespace set.** The `trim` operator, `split`'s per-element `trim` flag, `buildString`'s per-rendered-value `trim` flag and the runs `buildString`'s `closeGaps` consumes around an empty render all use the same character set (the JS `String.trim` set — WhiteSpace + line terminators) via one shared function; refining the set later moves every site together.
- **One code-point segmentation.** `split` with an empty delimiter and (confirmed in the batch-5 pass) `length` on strings count **Unicode code points**, never UTF-16 units — one shared helper (spread/`Array.from` semantics or an index-arithmetic equivalent), so no operator tears a surrogate pair while another counts it as two. A custom `substring` (cut from core — see the possible-custom-operators list) should consume the same helper. Grapheme clusters are recorded as out of scope in the passes; if that ever changes (`Intl.Segmenter`), it changes in one place.
- **Compiled-pattern reuse for `regex`.** A literal `pattern` compiles once at parse — the same moment `validate()` checks it (ledger #11) — and the compiled `RegExp` rides the compile artifact; dynamic patterns compile per evaluation. Global-scan state (`lastIndex`) must never leak between evaluations — construct or reset per use.
- **One path resolver.** `$data`-reference resolution and the `get` operator consume a single path-resolution function — missing/null drill-through, numeric segments (index against arrays, key against objects, however spelled), own-enumerable-properties-only lookup (no `__proto__` / `constructor` leakage) — so the sugar contract (`{ $get: 'a.b' }` ≡ `"$data.a.b"`, batch 6) holds by construction. `get`'s quoted-bracket and segments-array forms extend the same resolver rather than forking it; `strictDataPaths` is a flag on this one function.

## Null policies and boundary normalization live in the engine, not operator bodies

Two enforcement points suggested by the Type/coercion area, both engine-level so metadata stays honest (the same argument as `positionalParams` replacing 24 `parseChildren` functions):

- **Null-policy enforcement from metadata.** Each parameter's declared policy (`propagate` / `value` / `reject`, plus null-means-unset on optionals) can be applied generically by the engine _before_ the operator body runs: propagate short-circuits the node to `null`, reject raises the runtime type error, unset substitutes the layered default (per-node → `operatorDefaults` → metadata). Operator bodies then only ever see nulls on parameters declared `value` — hand-coded null checks inside operators should be a smell in review.
- **Boundary normalization.** `undefined` → `null` normalization happens at the engine's operator-result boundary (JSON-serialization semantics for JS-authored object values and array elements are handled once, at parse). A shared finite-number guard at the same boundary converts would-be `NaN`/`±Infinity` results into proper runtime failures with good messages, instead of each math operator policing its own output.

## Fragment machinery rides existing mechanisms

Two suggestions from the Fragments area ([v3-api.md → Fragments](v3-api.md#fragments--agreed)), both reusing machinery already described above:

- **Lazy arguments are the vars mechanism.** A fragment call instance is a scope object; static-mode arguments enter it as unevaluated thunks alongside the body's own `vars`, with the same promise memoization (the first `$params` reference stores the in-flight Promise; parallel references share it; rejections memoize too, per fallback rule 5's corner). Dynamic-arguments mode degenerates gracefully: the arguments node evaluates eagerly to an object and its keys enter the same scope as already-resolved values, so the body-side `$params` lookup is identical in both modes.
- **Shielding lifts through the call (Phase-11 planning, September 2026).** A registered body root carrying a constant `fallback` has its static fallback computed at registration and stored on the compiled fragment; a call node with no `fallback` of its own lifts it, so `staticFallbackFor` answers for a fragment-call hole the way it already does for an operator one. Amends obligation B2, where the rationale lives: the alternative is that wrapping an expression in a fragment quietly unshields it.
  _Built at Phase 11, both as described. The lazy-arguments bullet turned out to need nothing new: a thunk is already bound to the scope that DECLARED it rather than to whoever demands it first (src/evaluate/scope.ts records that ruling), so a fragment argument is that construction with the caller's context substituted. What the call adds is the frame the thunks live in — one per **declared** parameter rather than per supplied argument, which is what makes bare `$params` and dynamic mode's ignored extras fall out of one structure — and the sealing, which is the absence of two context fields rather than a check._

- **Bodies compile once, at registration.** The parse → compile pass (above) runs over each fragment body when it is registered — registration-time validation _is_ that pass, plus the signature checks (declared parameters, defaults vs types, required+default contradictions) and cycle detection over the static fragment-reference graph. A call site then splices a precompiled body; nothing re-parses per call. Replacing a fragment definition or the `operators` array re-runs registry validation and invalidates the parse cache (already required — step 4 above).

## `and` / `or` early resolution: a race with error parking

The parallel-with-cancellation semantics ([v3-operator-parameters.md](v3-operator-parameters.md), batch 1) suggests this shape: evaluate all operands concurrently under a per-node abort scope (an `AbortController` derived from the evaluation signal — the same chain the kill switch already threads). As each operand settles: a **decisive** value (falsy for `and`, truthy for `or`) resolves the node, aborts the scope, and everything still in flight is ignored; a **failure** is _parked_, not raised; a non-decisive value just counts down. If all operands settle without a decider: any parked failure fails the node — deterministically the lowest-_index_ parked failure, not the first to arrive — otherwise the identity result (`true` / `false`) returns. This makes the Kleene rule (an operand failure matters only if the result depends on it) fall out of the control flow rather than needing case analysis.

Notes: JS can't preempt a synchronous operator body, so cancellation lands at node boundaries and via the client-threaded signal — which is where the time lives anyway (network). Parked failures that lose the race never surface in `mode: 'report'` (per the spec); `trace` records per-operand status (value / failed-discarded / cancelled). Whether _sibling_ parked failures also appear in report output when the node does fail is a report-shape question for the Evaluator-methods area.

## Timeout shielding rides the compile artifact

The `fallback` rule-3 exception ([v3-api.md → `fallback` semantics](v3-api.md#fallback-semantics)) needs no evaluation-time machinery beyond what deep evaluation already builds. At parse: for each hole, precompute a `staticFallback` constant (present iff the hole's `fallback` subtree is classified constant), and derive one expression-level `shielded` flag (every hole has one). On timeout: if unshielded, throw/report; if shielded, splice each hole's completed result — or its precomputed static-fallback constant where incomplete — into the constant skeleton and return. Pure constant assembly, no evaluation after the deadline. The same precomputed flag powers the `validate()` / editor "timeout-shielded" badge.

_Built (Phase 10, September 2026): the assembly is one function in [src/evaluate/run.ts](../../src/evaluate/run.ts), and the "no evaluation after the deadline" clause holds by construction rather than by discipline — **each hole is raced against the root's expiry**, which on the deadline hands back the hole's static fallback where the hole has not yet won. A promise reaction is a microtask and the timer's callback a macrotask that runs only once the queue has drained, so a hole that finished before the deadline has already won its race; one that had not cannot win afterwards, because `deadline()` registers its abort listener before any node's scope does, making the expiry's rejection the first reaction queued in the dispatch. The cut is exact, and the mechanism is the same primitive the unshielded path uses — the first cut kept a slot table, an abort listener and a swallow branch of its own, and the PR review collapsed all three into the race. Three details the mechanism needed. The kill switch is the **root of the same scope chain** the nodes already use: a `deadline()` (the Phase-9 `requestDeadline` with its reason made a parameter, in [src/evaluate/abort.ts](../../src/evaluate/abort.ts)) whose parent is the caller's `signal` and whose timer is the `timeout`, built for every evaluation and settled with it like any node scope — so an uncaught failure in one hole cancels its siblings' in-flight requests through the chain, kill switch or not, and a body's `context.signal` is aborted once the call has returned. `abortedOutcome` classifies the root's abort **by reason** — the timeout marker, "settled", or anything else meaning the caller — so a boundary crossed after the call returned is silent abandonment rather than a phantom `aborted` error. And the unshielded case is a `Promise.race` of the evaluation against the root's expiry, expiry first: the abort dispatch rejects it before any node boundary can observe the signal, so the caller always receives the root-level error (path `[]`, naming the budget) rather than whichever node noticed first, and a driver that ignores its signal cannot hold the call past its deadline — the case Phase 9 left open. Two corners caught at review before they shipped: a caller's signal already aborted at entry is answered once at the top of the run, with the root's error (path `[]`) — left to the races, the first hole boundary to notice would win, a race between settled promises going to the one with fewer hops; and a literal carrying only a comment key or a vars block is not inert yet compiles to a constant with `holes = []`, making `shielded` vacuously true — it takes the plain path, nothing in it being able to time out. Readings recorded: the clock starts after the static gate, the compile being synchronous and uninterruptible anyway; a result arriving after the deadline is still written to the result cache, writing not being evaluation; `timeout` must be a positive finite number of ms, `undefined` being the one spelling of "no deadline". The three concerns live apart on purpose — mechanism in `abort.ts`, meaning (what a reason implies) in `internal.ts`, policy (when to race, what to assemble) in `run.ts` — and the recursive evaluator is wrapped, not forked: every node still goes through `evaluateNode`._

_Generalized at Phase-12 planning (September 2026, Carl): the per-hole race becomes one composable **hole boundary**, and `evaluateShielded` dissolves into it._ Report mode wants exactly the same thing the shielded timeout wants — something wrapped around each root hole, one hole at a time — and trace wants the artifact root to have an entry, which the shielded path prevented by mapping the holes itself instead of going through `evaluateNode(artifact.root)`. So `run.ts` keeps building the policy and stops applying it: it composes a boundary function from the mode and the root deadline, and the root skeleton applies it to each of its holes (a node root's single hole being the root, the boundary wraps the call instead). The composition order is fixed and is the whole of the semantics — the expiry race sits OUTSIDE the report catch, because a kill switch must end the evaluation where an ordinary failure degrades a hole. What this does not move is the mechanism: the race is still a race against `root.expiry`, `deadline()` still registers its listener before any node scope does, and the microtask-before-macrotask argument above is untouched — the closure is merely built in one file and invoked in another. Three shapes fall out of one: report alone catches, a shielded timeout alone races, and the two together compose without either knowing about the other.
